# Крайние случаи (M6)

> **С 2026-11-14 Swift-реализация выведена из рабочего дерева.** Канонический Rust-порт живёт в `rust/`, актуальные команды и правила — в корневом `AGENTS.md` и `rust/STATUS.md`; Swift-код сохранён git-тегом `swift-oracle`. Заметка ниже описывает Swift-эпоху.

Направление M6: защита от зависаний, чёрного экрана и перезапускных бурь. Упаковка — отдельная сессия.

## Итерация 1 (2026-11-03): устойчивость к стойлам и битому конфигу

### Зависание после сна/остановки процесса
`SimulationScene.tick` брал `dt = now - lastTime` без ограничения и считал `Int(accumulated / stepSize)`. После sleep/wake `dt` — секунды/минуты, значит десятки тысяч шагов за один кадр; при `stepSize = 0` — `Int(infinity)` и краш.

Введён чисто ядерный `SimulationStepScheduler` (`Core/.../SimulationStepScheduler.swift`):
- `dt` ограничивается `maximumFrameInterval` (по умолчанию 0.1 с);
- число шагов за кадр ограничено `maximumStepsPerFrame` (4096) — страховка на случай крошечного `stepSize`;
- при упоре в cap накопленный «долг» сбрасывается, а не переносится: после сна не нужно догонять пропущенное время;
- нефинитные/неположительные `dt`, `stepSize`, `simulationSpeed` дают 0 шагов вместо краша.

`SimulationScene` клампит `dt` тем же `maximumFrameInterval` и до камеры/цвета, чтобы после сна не прыгали орбита и градиент.

Итог: максимальная работа после стойла — `speed * 0.1 / stepSize` шагов (у каталога ≈ 75), а не десятки тысяч. `O(n)`-сдвиг `trace.removeFirst()` на каждом шаге остаётся, но ограничен.

### Битый конфиг не должен гасить заставку
`AttractorCatalog.validate(_:)` / `bundledValidation()` проверяют каждый дескриптор и **отбрасывают только плохие**, возвращая `AttractorCatalogValidation` (`valid` + `issues`):
- пустой каталог;
- пустой/дублирующийся `id`;
- диапазоны: конечность, `min <= max`; `stepSize > 0`, `simulationSpeed > 0`, `cameraRotationSpeed/trailColorSpeed >= 0`, `trailLength >= 2`;
- параметры: непустые, уникальные, не совпадают с `x/y/z`;
- формулы: парсятся, ссылаются только на `x/y/z` + объявленные параметры. Для этого у `Expression` появилось `referencedVariables`.

Хост (`ScreensaverView.startSimulation`) и демо (`main.swift`) используют `bundledValidation()`: issues пишутся в лог/`stderr`, выбор идёт из `valid`. Пустой `valid` → запись в лог и без краша (показывать нечего только при полностью сломанном бандле).

### Ошибка вычисления формулы больше не «замораживает» кадр
Было: `guard let advanced = try? engine.advance() else { continue }` — при доменной ошибке (`sqrt`/`ln` от недопустимого значения) шаги молча пропускались, трейс навсегда замирал на последней точке, монитор здоровья ничего не видел (он получает только успешные состояния).

Теперь ошибка `engine.advance()` → `requestRestart(reason:)` (общий путь с health-monitor): сцена останавливается, хост делает новый случайный выбор. В демо с явными аргументами (`healthMonitor == nil`) перевыбор по-прежнему отключён — остаётся застывший кадр и лог, это режим отладки.

## Итерация 2 (2026-11-03): restart storm
Если запуск падает сразу, health-monitor/ошибка формулы могли перезапускать сцену в цикле.

`RestartLimiter` (ядро, инжектируется `now`):
- скользящее окно (`window = 10 с`, `maximumRestarts = 3`);
- `allowRestart(at:)` записывает перезапуск, пока бюджет не исчерпан;
- `nextRetryTime(after:)` — когда освободится слот (самый старый перезапуск + окно); `reset()` — при новом показе.

Хост: `restartSimulation` спрашивает лимитер. Отказ → `Timer` с отложенным повтором (`nextRetryTime`), а не пересоздание сцены каждый кадр. `tearDownScene`, `stopAnimation`, детач view отменяют отложенный таймер. `startAnimation` сбрасывает лимитер. Ошибка `startSimulation` (после валидации маловероятная) тоже уходит в `restartSimulation`, чтобы не оставить чёрный экран.
Демо: тот же лимитер; при отказе остаётся последний кадр и запись в лог (режим отладки).

## Итерация 3 (2026-11-03): валидация демо-CLI
`SimulationSettings.validationIssues` (ядро) отвергает:
- `stepSize <= 0` или нефинитный;
- отрицательные/нефинитные `simulationSpeed`, `cameraRotationSpeed`, `trailColorSpeed` (ноль разрешён — осознанная заморозка для отладки);
- `trailLength < 2` (иначе `TraceRenderer` возвращает пустую геометрию).

`Demo/main.swift` печатает все issues в `stderr` и выходит с кодом 2 **после** применения `--step/--speed/--trail-length/...`, поэтому любой источник значений проверяется одинаково. Проверено вручную: `--step 0` и `--trail-length 1` → exit 2 с внятным сообщением; `--help` работает.

## Итерация 4 (2026-11-03): ручной smoke и переустановка
- Превью после пересборки падало с `SIGKILL (Code Signature Invalid) / Invalid Page`, хотя подпись валидна: бандл обновили копированием **поверх** существующего каталога, бинарник перезаписался в том же inode, который уже был отображён в `legacyScreenSaver`. Переустановка через `rm -rf` + `ditto` восстановила превью, `dlopen_preflight` снова `true`. Подробности — `mem:saver_install`.
- Превью работает: старт/стоп, отрисовка, формулы/параметры.
- Мультимониторность: на машине **один активный дисплей** (`CGGetActiveDisplayList == 1`), поэтому сценарий на железе не проверен. Архитектурно каждый `ScreensaverView` создаёт независимые `SimulationScene` и `Timer`, общего изменяемого состояния нет; единственный риск — ложный teardown при перекладывании view между экранами.
