**Стек и версии:**
- Язык: **Swift 6.3** (swiftlang-6.3.3, clang-2100.1.1.101), таргет `arm64-apple-macosx26.0`.
- ОС: macOS 26.6.2, arm64 (Apple Silicon).
- Фреймворки: **SceneKit** (рендер), Foundation/**NSExpression** (парсинг формул), Codable/JSON (конфиг), ScreenSaver/`.appex` (хост-скринсейвер), QuartzCore (display link).
- Внешних сторонних зависимостей в проекте НЕТ (по договорённости минимизируем зависимости, только Apple-фреймворки).
- Формат скринсейвера: современный `.appex` (не легаси `.saver`).

**Структура и расположение бизнес-логики:**
- Основная бизнес-логика — **чистое ядро как SPM-модуль** (модель, конфиг, ODESolver, AttractorEngine, случайный выбор). Оно тестируемо через `swift test` в этой среде.
- UI-рендер (SceneKit) и хост-оболочка `.appex` — отдельные таргеты (требуют Xcode, которого в этой среде нет).
- Документация и память проекта: `.serena/memories/` (architecture.md, domain_model.md, development_guide.md). README.md — точка входа.

## 3. Architecture & Patterns

**Ключевые паттерны проекта (обнаружены через Serena):**
- **Чистое ядро vs рендер/хост:** вся логика (модель, конфиг, ODESolver, AttractorEngine, выбор) — в тестируемом SPM-модуле без зависимости от UI. Рендер (SceneKit) и `.appex` — отдельные таргеты поверх ядра.
- **Описание аттракторов данными:** аттракторы описываются в `attractors.json` (формулы строками, параметры и гиперпараметры диапазонами `[min,max]`), а не кодом. Добавление аттрактора не требует правки кода.
- **Формулы как данные через NSExpression:** строки формул dX/dY/dZ парсятся `NSExpression` с подстановкой параметров как переменных.
- **Численное интегрирование:** `ODESolver` — RK4 (основной) + Euler (для гиперпараметра «длина шага/точность`), метод `step(state, params, dt)`.
- **Слой выбора:** `Randomizer` (случайный аттрактор/параметры/гиперпараметры) и `DebugConfig` (ручные параметры) питают движок.
- **Разделение типов:** `AttractorModel` (состояние x,y,z + параметры + NSExpression), `SimulationHyperparameters` (гиперпараметры), явные типы вместо голых кортежей/чисел.
- **Тестируемость ядра:** для каждого публичного символа — юнит-тест.

**Запрещённые приёмы (антипаттерны), которые ломают архитектуру:**
- НЕ смешивай логику ядра с UI-кодом SceneKit/AppKit (нарушит SPM-тестируемость).
- НЕ встраивай параметры/формулы аттрактора хардкодом в код — только через конфиг (`attractors.json`).
- НЕ добавляй внешние зависимости без необходимости — сначала Apple-фреймворки; новую зависимость — только по согласованию.
- НЕ пиши универсального «магического» численного интегратора с неявными допущениями и без тестов на сходимость/эталон; не меняй шаг/алгоритм, не проверив влияние на известные аттракторы (Лоренц r=28 и т.п.).
- НЕ разбивай состояние на несвязанные голые переменные там, где нужен явный тип `State`.
- НЕ редактируй файлы напрямую (в обход Serena) — рискуешь стереть соседний код.

## 4. Implementation & Tooling

**Инструменты Serena для точечного редактирования (используй их обязательно):**
- Чтение/понимание: `get_symbols_overview`, `find_symbol` (+`include_body`, `depth`), `find_referencing_symbols`, `find_implementations`, `read_file` (чанками при необходимости), `list_dir`.
- Поиск: `search_for_pattern` (regex по коду).
- Редактирование на уровне символов (замена целых типов/методов, рефакторинг): `replace_symbol_body`, `insert_after_symbol`, `insert_before_symbol`, `rename_symbol`, `safe_delete_symbol`.
- Редактирование строчное, нескольких мест/файлов: `replace_content` (regex/literal), `replace_in_files` (с `dry_run` → `occurrence_ids`, чтобы не задеть лишнее).
- Метаданные/память: `write_memory`, `list_memories`, `create_text_file` (для новых файлов), `get_diagnostics_for_file`.
- Для новых небольших файлов — `create_text_file`; для существующих — символьные/строчные правки, НЕ переписывай весь файл целиком без нужды.
- Перед массовой правкой обязательно используй `dry_run` в `replace_in_files` и проверяй `expected_count`, чтобы случайно не стереть соседний код.
- После редактирования проверяй типы: `get_diagnostics_for_file`.

**Проверка кода линтером и тестами:**
- Тесты ядра: `swift test` (из SPM-пакета ядра), выборочно `swift test --filter <Символ>`.
- Сборка-проверка: `swift build`.
- Диагностика типов/ошибок компиляции: `get_diagnostics_for_file` (min_severity=1 для ошибок).
- В этой среде нет `xcodebuild` — проверка ядра через SPM; таргеты `.appex`/демо-UI проверяются на машине с Xcode (документируй в `.serena/memories/`).

## 5. Self-Healing & Definition of Done

**Если тесты упали (алгоритм):**
1. Не паникуй и не «исправляй вслепую». Прочитай вывод фейла: какой тест, какой символ, какие значения ожидались/получились.
2. Локализуй причину: `get_diagnostics_for_file` для затрагиваемых файлов; при необходимости `find_referencing_symbols`/`read_file` — проверь логику, которую трогал.
3. Определи тип ошибки: (а) сам код неверен → исправь через Serena; (б) тест устарел/не поспевает за архитектурой → уточни и приведи тест к действующему контракту; (в) тест красный был ещё ДО твоих изменений → не «чини» молча, сообщи об этом.
4. После исправления перезапусти именно упавший тест, затем весь набор. Итерация до зелёного.
5. Если не находишь причину за разумное число итераций — сообщи пользователю с деталями вывода, а не закоммить красное.

**Definition of Done — финальный чек-лист перед отдачей на ревью:**
- [ ] Активен правильный майлстоун/ветка (не `main`).
- [ ] `swift test` (ядро) — зелёный; затронутые новые/изменённые символы покрыты тестами.
- [ ] Cборка `swift build` — без ошибок; `get_diagnostics_for_file` не показывает ошибок в изменённом коде.
- [ ] Внесены точечные, минимальные изменения через инструменты Serena (не переписывал файлы целиком без нужды).
- [ ] Нет неиспользуемого/мёртвого кода и забытых `print`/дебаг-артефактов.
- [ ] Форматирование/стиль соответствует `development_guide.md` (комментарии кода — англ., документация — рус.).
- [ ] Обновлена память проекта `.serena/memories/`, если появилось новое решение/паттерн/изменение контракта (дополни существующий файл или создай новый; зафиксируй в README статус майлстоуна в «Дорожной карте»).
- [ ] Сделан атомарный коммит с осмысленным сообщением (по смыслу, на английском).
- [ ] Резюме для пользователя: что сделано, что не сделано и почему, какие проверки пройдены.
